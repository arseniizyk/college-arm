## Бизнес-логика и целостность данных

### B6. `sequelize.sync({ alter: true })` на каждом старте
`server/index.js:34`

```js
await sequelize.sync({ alter: true })
```

При каждом запуске Sequelize сверяет модель со схемой и может выполнить `ALTER TABLE` по живой базе — в том числе на боевом postgres из контейнера. Схема меняется без миграций и без возможности отката; структура таблиц зависит от состояния, в котором сервер последний раз выключали.

Это же следствие того, что новые колонки (`Student.userId`, `Teacher.userId`) появляются только при ближайшем `sync({ alter: true })` — до этого прогона фичи B1/B12 на живой базе не работают.

**Фикс:** `sync()` только в dev-режиме (по `NODE_ENV`), в production — Sequelize CLI-миграции. Отдельная находка: `DatabaseError` глушится общим `catch` в `index.js` (`console.log(e)`), после чего сервер просто не поднимается без внятного сообщения.

## Баги и расхождения в клиенте

### C9. Порядок заявок в «Обработке заявок»: карточка уезжает из-под курсора, страница может остаться пустой
`client/src/components/RequestsManagement.jsx:49-61` (сортировка), `:67-70` и `:73-75` (пагинация)

**Как сейчас.** Сервер отдаёт `order: [['createdAt', 'DESC']]` (`server/controllers/requestController.js:198`), но админская вкладка «Обработка заявок» рендерится отдельным компонентом `RequestsManagement` и **пересортировывает** выдачу: сначала `statusPriority` (`pending (1) → completed (2) → cancelled (3)`, `client/src/utils/requestStatus.js:10,21,32`), внутри группы — `createdAt` DESC. Порядок сервера для этой вкладки не имеет значения.

**Что не так:**

1. **Карточка уезжает из-под курсора при смене статуса.** Админ жмёт «Завершено» на верхней заявке → она переезжает в конец группы `completed`, то есть за пределы текущей страницы (в `ITEMS_PER_PAGE` = 10 заявок помещается). Список перерисовывается, позиция скролла теряется. Обработать пачку заявок подряд нельзя — после каждого действия приходится искать глазами, где ты был.
2. **`isViewed` в сортировке не участвует.** «Новая заявка» — это `pending && !isViewed` (`client/src/utils/requestStatus.js:47`), но в приоритетах её нет. Непросмотренная заявка, созданная вчера, окажется ниже просмотренной, созданной сегодня утром. Счётчик на бейдже таба (`Admin.jsx:18`) считает одно, список показывает другое.
3. **`currentPage` не клампится к `totalPages`.** Сброс есть только в `useMemo` по `[searchTerm, statusFilter]` (`:73-75`), и это `setState` во время рендера — анти-паттерн, отсюда же `react-hooks/exhaustive-deps` warning на этой строке. После смены статусов или автообновления раз в минуту (`Admin.jsx:21-41`) число страниц может упасть: `slice` (`:70`) отдаёт пустой массив → «Заявки не найдены» при непустом списке. Из `Pagination` (`Pagination.jsx:49`) такую страницу не покинуть: `disabled={currentPage === totalPages}` при `currentPage = 3`, `totalPages = 2` даёт не-disabled «Вперед», который прыгает на страницу 4.
4. **Группы статусов разрезают пагинацию.** При 10 `pending` и 20 `completed` страница 1 будет целиком из `pending`, страница 2 — из `completed`, без заголовка-разделителя. Непонятно, где кончилась группа.
5. **Третья копия сортировки.** `client/src/hooks/useAdminLogic.js:274-276` сортирует заявки по `createdAt` для табличного пути. Он достижим: в `DataManagement` есть вкладка «Заявки» (`DataManagement.jsx:201-225`) с обычным `TableContent`. То есть заявки показываются в админке дважды, в табличном виде (`createdAt` DESC, все статусы вперемешку) и карточками (по статусам) — с разным порядком в одном экране.

**Как проверить:** зайти под ADMIN, вкладка «Обработка заявок», сортировать по ID; нажать «Завершено» на первой карточке в `pending` — она прыгает в конец списка/на другую страницу. Затем встать на последнюю страницу и сменить статус нескольких заявок так, чтобы вкладок стало меньше, — список покажет «Заявки не найдены» при общем количестве больше нуля.

**Фикс:** убрать сортировку по статусу из общего списка — сортировать по `!isViewed` (новые сверху), затем `createdAt` DESC; статус-приоритет оставить только в уже существующем фильтре и сортировке табличного пути, чтобы два экрана не противоречили друг другу. Разделители групп, если они нужны, — как отдельный визуальный слой, не как порядок сортировки, иначе любая смена статуса снова двигает список. `currentPage` клампить к `totalPages` в рендере, сброс фильтров перенести из `useMemo` в `useEffect`. Третью копию в `useAdminLogic.js` удалить, оставив одну сортировку на оба экрана.

### C8. Поля, которых нет в колонках таблицы
`client/src/utils/tableConfig.js:37` (`supervisor`), `:40` (`course`), `:46` (`duration`) — в исходной формулировке номера строк неверные

Колонки `supervisor`, `course`, `duration` не соответствуют полям API — `TableContent` и `TableCell` обрабатывают их вручную. Работает, но конфигурация перестала быть источником правды: любая новая колонка потребует правки в трёх файлах.

**`supervisor` не мёртвая колонка:** `groupController.get` отдаёт ровно это дерево (`Group.hasOne(Supervisor)` → `Supervisor.belongsTo(Teacher)`), и то же вложенное `group.supervisor.teacher` читают `ReleaseOrderModal.jsx:44`, `HealthOrderModal.jsx:44`, `StudentDirectionOrderModal.jsx:49`. Мёртвая запись `supervisors` в `DataStore.ENTITY_TYPES` — заготовка под **S1**, см. [issues-solved.md](issues-solved.md).

`course` и `duration` работают через `value={null}` + передачу всего `item` в `TableCell.jsx:9-39`, причём обе ветки стоят **до** null-guard'а (`:42-44`).

**Фикс:** пометка `{ key: 'course', computed: true }` безопасна и рендера не меняет. Рефакторинг рендера — только вместе с удалением `TableCell.jsx:9-39`, иначе `value={null}` перестанет работать: сам по себе он эти ветки больше ниоткуда не вызывает.

## Недостающая функциональность

### S1. Нет управления кураторами как отдельной сущностью
`server/routes/` (нет `supervisorRouter.js`), `client/src/components/DataManagement.jsx` (7 вкладок, «Кураторы» нет)

По [Пояснительной записке.docx](Пояснительная%20записка.docx) в списке администрируемых сущностей прямо стоят «пользователей, групп, **кураторов** и форм отчётности» (`doc.txt:28`, `:245`). Сейчас куратор назначается только как побочный эффект выбора преподавателя в группе, отдельного списка кураторов нет.

**Фикс:** `supervisorController` + `supervisorRouter` (`GET /api/supervisor` с `include: [{ model: Group }, { model: Teacher }]`) + вкладка «Кураторы» в `DataManagement`/`tableConfig`. Требует отдельного этапа: это новая функциональность, а не чистка.

⚠️ Один куратор на группу (`Group.hasOne`) — ограничение на уровне схемы не выражено, `groupController.create` (`:36`) создаёт `Supervisor` без `findOrCreate` и потому упадёт на повторе, а `sync({ alter: true })` не добавит уникальный индекс (см. B6).
